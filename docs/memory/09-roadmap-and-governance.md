# 完善路线图与治理机制

## 总体判断

NanZi 已经具备复杂企业内部平台的功能宽度。下一阶段应该优先做收敛、可信和可恢复，而不是继续无边界增加功能。

在 P0 安全问题关闭、备份恢复和高可用演练通过前，不应作为公网多租户平台上线，也不应宣称已经具备生产级多租户、代码沙箱和高可用能力。

## 阶段 0：风险止血（0-2 周）

| 目标 | 工作 | 退出证据 |
|---|---|---|
| 关闭直接入侵路径 | 关闭/隔离代码执行、修复权限和 SPA 穿越 | 权限矩阵、路径穿越和 Sandbox 测试 |
| 保护浏览器与 Embed | HTML 禁用和清洗、CSP、Origin/Source/nonce、短期 Token | 恶意 Markdown 和跨域浏览器测试 |
| 消除已知凭据 | 删除固定管理员 Key 和默认长期 Secret，轮换现有环境 | Secret Scan、Bootstrap 和轮换记录 |
| 阻止 SSRF | MCP、模型、工具和 Webhook 使用统一出网策略 | Redirect、Rebinding、IPv4/IPv6 和元数据测试 |
| 修复数据越权 | 删除 ChatBI `bypass_table_auth` | 所有 SQL 入口的跨用户负向测试 |

本阶段暂停新增公网外部集成，除非该改动直接用于关闭 P0。

## 阶段 1：工程稳定（2-6 周）

| 方向 | 交付内容 |
|---|---|
| 工程 | 依赖锁、CI、类型/Lint/单测/集成/构建门禁，明确事务边界 |
| 前端 | 统一认证、API、SSE Transport 和 Store；抽取 ChatRuntime；路由懒加载 |
| 运行时 | `/live`、`/startup`、`/ready`、Graceful Drain、持久化 Execution 和有界队列 |
| 运维 | 结构化日志、Metrics、OpenTelemetry、告警、Dashboard 和容量预算 |
| 数据库 | 迁移 Ledger/Checksum/Lock，MySQL/PostgreSQL Fresh/Upgrade 测试 |
| 恢复 | DB PITR、Redis/对象存储策略和第一次完整恢复演练 |
| 产品 | 简化导航，提升数据门户和场景入口，建立核心业务漏斗 |

工程稳定当前进展：已建立 GitHub Actions 四类质量 job、增量 Ruff/SAST 棘轮、前后端离线测试、
Secret/依赖/镜像扫描证据和 CycloneDX SBOM；Python Runtime/Dev 已拆分但完整 lock、远端首次跑绿、
Mypy 存量清零及漏洞报告硬门禁仍未完成。

退出条件：没有未关闭 P0；P1 必须有 Owner 和期限；CI 强制执行；备份恢复完成；双副本 Smoke/故障测试通过。

## 阶段 2：平台化（2-4 个月）

- 拆分无状态 API、推理 Worker、隔离工具/代码 Worker、Scheduler 和 Profiling/Index Worker。
- 建立持久化执行事件、Lease/Heartbeat、幂等、重试、死信和跨副本取消。
- 将 Skills、上传和生成文件迁移到对象存储，拆分 Redis 状态与向量负载。
- 实现贯穿所有领域的 Tenant/Workspace 模型和存量数据回填。
- 建设 Agent 评测中心：数据集、人工/模型/规则评分器、回归基线和路由/工具/引用指标。
- 建设发布生命周期：开发/预发/生产、审批、质量门禁、灰度、版本对比和回滚。
- 将硬编码场景升级为受治理资产包，增加条件、并行、人工审批和补偿节点。
- 强化 ChatBI 语义治理和知识反馈到治理任务的闭环。

退出条件：持续达到 99.9% SLO；故障切换和恢复演练通过；跨租户测试通过；Agent 可以一键回滚；生产发布受评测门禁控制。

## 阶段 3：产品增长（4-9 个月）

- 建设 Connector、Skill、MCP 和场景的企业私有市场，支持签名和兼容性。
- 发布类型化、版本化 Embed SDK，提供 Token Exchange、Telemetry 和集成测试包。
- 建设成本归集、预算、Showback/Chargeback 和业务 ROI。
- 增加跨 Agent 工作流、人工队列、SLA、升级和补偿。
- 建设会话、任务、报表和知识的组织级统一搜索。
- 完成国际化、WCAG 2.2 AA 和聚焦任务处理的移动/PWA 体验。
- 形成带升级契约和验收基准的行业场景包。

## 建议 Owner

| 方向 | 负责角色 | 协作方 |
|---|---|---|
| 安全架构和事件响应 | 安全负责人 | 后端、前端、SRE |
| 执行与运行时协议 | 平台后端负责人 | AI 工程、SRE |
| 数据和语义可信 | 数据平台负责人 | 产品、安全、BI Owner |
| 产品 IA、评测与发布 | 产品负责人 | 前端、设计、AI 评测 |
| 可靠性和灾备 | SRE 负责人 | DBA、平台、安全 |
| Tenant/Workspace | 平台架构师 | 全部领域 Owner |

延期的 P1/P2 必须记录风险、影响资产、补偿措施、Owner、截止时间和批准人。“已知问题”但没有期限不等于完成风险接受。

## 治理指标

| 维度 | 指标 |
|---|---|
| 可信 | 有依据回答率、引用完整率、SQL 正确率、审批绕过数 |
| 业务 | 成功任务率、报表采纳、节省时间、场景验收率 |
| 可靠性 | 可用性、首 Token 延迟、完成率、Scheduler Lag、重复副作用 |
| 安全 | Critical 存量时间、Secret/SSRF/XSS 回归、隔离测试通过率 |
| 交付 | 变更失败率、回滚时间、评测拦截数、迁移成功率 |
| 成本 | 单次成功任务成本、Token/工具/数据源成本、预算偏差 |

## 生产就绪定义

生产就绪意味着：P0 全部关闭；部署支持自动升级和回滚；Secret 外部管理；最小权限和租户隔离通过测试；每个 Run 可观测；备份能在目标时间恢复；故障演练通过；容量有余量；值班 Runbook 可执行。功能丰富或单机能够启动，并不等于生产就绪。
